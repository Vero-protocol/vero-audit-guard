# Verifiable Audit Trail

`verifiable-audit-trail` hashes audit reports generated by `scanner-engine`, anchors their complete SHA-256 digests on Stellar, and verifies local report bytes against a specific on-chain transaction.

## Security model

A verification requires two trusted references:

- The transaction hash identifies the exact anchor to retrieve from Horizon.
- The public anchor account identifies who was authorized to create that anchor.

New anchors use Stellar `MEMO_HASH`, which stores the complete 32-byte SHA-256 digest. Historical anchors created by older versions used a truncated `MEMO_TEXT` identifier. That legacy format is rejected by default and can only be enabled explicitly.

Verification hashes the file's raw bytes. Reformatting otherwise equivalent JSON changes its digest and is treated as a mismatch.

## CLI usage

Build before invoking the entry point:

```bash
npm run build
```

### Anchor reports

```bash
node dist/index.js anchor ../reports
```

Every `.json` file in the directory is hashed. When `AUDIT_KEYPAIR_SECRET` is configured, each complete digest is submitted as a `MEMO_HASH`; otherwise the command is a dry run.

The historical directory-only invocation remains supported:

```bash
node dist/index.js ../reports
```

### Verify a report

```bash
node dist/index.js verify ../reports/latest-scan.json \
  --tx <64-character-transaction-hash> \
  --account <G...-anchor-public-key>
```

`--account` can be omitted when `AUDIT_ANCHOR_ACCOUNT` is configured. If both are supplied, they must identify the same account; a CLI argument cannot replace the configured trust anchor.

Verification checks that:

1. Horizon returns the requested transaction.
2. The transaction was successful.
3. Horizon returns the same transaction hash that was requested.
4. `source_account` matches the trusted public anchor account.
5. The transaction contains a canonical 32-byte `MEMO_HASH`.
6. The on-chain digest exactly matches the SHA-256 of the local file.
7. The local file did not change while the Horizon lookup was in progress.

### Verify a historical legacy anchor

Older versions stored only the first 22 hexadecimal characters of the digest in a `vero:` text memo. Enable this weaker format only when verifying a known historical transaction:

```bash
node dist/index.js verify ../reports/latest-scan.json \
  --tx <64-character-transaction-hash> \
  --account <G...-anchor-public-key> \
  --allow-legacy-memo-text
```

A successful legacy verification prints a warning because it compares an 88-bit prefix rather than the complete SHA-256 digest.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | The report was verified successfully, or anchoring/dry-run completed. |
| `1` | Invalid invocation, configuration, local file, or Horizon operational failure. |
| `2` | Integrity failure: missing/failed anchor, wrong source account, invalid memo, or hash mismatch. |

Integrity failures emit a structured security incident to standard error. Horizon availability failures also fail closed, but are reported separately from evidence of tampering.

## Environment variables

| Variable | Description | Default |
| --- | --- | --- |
| `HORIZON_URL` | Horizon endpoint used for anchoring and exact transaction lookup. | `https://horizon-testnet.stellar.org` |
| `HORIZON_TIMEOUT_MS` | Verification lookup timeout in milliseconds, from `1` through `120000`. | `10000` |
| `STELLAR_NETWORK` | Stellar network used when signing anchors: `testnet` or `mainnet`. | `testnet` |
| `AUDIT_KEYPAIR_SECRET` | Secret key used only to sign new anchors. Leave empty for dry-run hashing. | *(empty)* |
| `AUDIT_ANCHOR_ACCOUNT` | Trusted public account required for verification. When anchoring, it must match the configured secret. | *(empty)* |

Verification never requires `AUDIT_KEYPAIR_SECRET`.

npm ci
